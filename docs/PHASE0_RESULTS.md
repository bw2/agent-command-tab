# Phase 0 results

Answers to the questions in [PLAN.md](PLAN.md) section 16, as they are settled. Machine: macOS 27.0.1, iTerm2 3.7.6, Claude Code 2.1.302, Codex 0.154.0 (0.163.0 for the live Codex tests), `iterm2` package 2.30, Python 3.13, PyObjC 12.2.2. Scripts are in [`spikes/`](../spikes/).

## Settled

| Question | Answer | How checked | Effect on the plan |
|---|---|---|---|
| Can the app connect to iTerm2 without `NSAppleScript`, from a background thread, including after a stale token? | Yes. Setting `iterm2.auth.gAppKitAvailable = False` once at startup makes the package always fetch its token with the `osascript` subprocess runner, including its own retry after a rejected token. Both a fresh and a stale token connected from a background thread's asyncio loop, and the `NSAppleScript` runner was never called. | `spikes/iterm2_connection_without_nsapplescript_spike.py` | Simpler than the planned wrapper around `Connection.authenticate`: one flag, set before the first connection. |
| Does a second connection in the same process work? | No. The second `async_create()` in one process failed with `ConnectionClosedError`, because the package's global `App` object stays bound to the first connection. | Same spike, two connections in one process | Confirms the plan's choice to restart the process to reconnect (section 4). |
| Does `claude agents --json` depend on the config folder? | Yes. With the default folder it listed 3 interactive sessions; with `CLAUDE_CONFIG_DIR=~/.claude_work` it listed a different session. | Ran both | Run it once per configured config folder (section 7), as planned. |
| Which file holds Codex hooks, and is a feature flag needed? | `~/.codex/hooks.json` (plain JSON). The `hooks` feature is stable and on by default. Codex records each hook's approval in `~/.codex/config.toml` under `[hooks.state."<hooks.json path>:<event>:<i>:<j>"]`, written by its `/hooks` screen. | `codex features list`; the local files | The installer only edits `hooks.json`; no TOML writing is needed. The user still approves new hooks in `/hooks`. |
| Does Codex still write rollout files, and are the migration features on? | Yes, rollout files are still written for new sessions (several from today). `background_paginated_rollout_migration` and `transcript_v2` are "under development" and off. | `codex features list`; `~/.codex/sessions/2026/10/18/` | The Codex readers work today; the migration remains a known future risk. |
| How do you get a monitor's display UUID without extra dependencies? | `CGDisplayCreateUUIDFromDisplayID` is not in PyObjC's Quartz package, but a `ctypes` call into Apple's ColorSync framework works (display number from `NSScreen.deviceDescription()["NSScreenNumber"]`, then `CFUUIDCreateString`). | `ctypes` test on this Mac | No Quartz dependency for the UUID. Quartz is needed only if the window-order fallback is needed. |
| How long does a full-screen read take? | 7 to 33 ms per call (median per session), 71 lines each, for 4 sessions. | `spikes/screen_read_timing_spike.py` | Cheap for a few sessions, but every 3 s for 20 hookless sessions it would be roughly 5 to 10% of one core. Run the screen fallback only for sessions with no other status source, and consider 5 s instead of 3 s. |
| How long does a standard-library-only hook forwarder take per event? | About 30 ms median (35 to 39 ms worst) with a 100 KB payload, whether or not the app is listening. Almost all of it is Python startup. | `spikes/hook_forwarder_timing_spike.py` | Acceptable because the hooks are registered as async, so agents don't wait. The installed entry point must not import anything heavy. |
| Prompt history files | `<config folder>/history.jsonl` (fields `sessionId`, `timestamp`, `project`, `display`, `pastedContents`) and `~/.codex/history.jsonl` (`session_id`, `ts`, `text`); 3.4 MB and 0.5 MB here. | Read the last line of each | Used for startup order (section 8). |
| Status function and variables | `iterm2.get_session_status` returns `status`, `turn_open`, `detail`, `text_color`, `dot_color`, `background_tasks`. The `status` variable read `idle` and `working`. Claude Code's `jobName` is its version number, so detection uses `commandLine`. | Earlier read-only checks (section 3 of the plan) | As planned. |
| Does "send text at start" work through a raw profile key? | Yes. `LocalWriteOnlyProfile({"Initial Text": command})` plus the custom-directory setters started the command in every new tab and window. | `spikes/test_window_experiments_spike.py` | Use it for new agent sessions (R13, R13.1); the prompt-wait fallback isn't needed. |
| Does `Window.async_set_tabs` move a tab to another window without interrupting its program? | Yes, for a shell loop. A counter printing 5 lines a second went from 16 to 26 across the move (a restarted shell would start again at 1); the tab got the new window's tab list. To repeat with a live agent turn. | Same spike | R18 as planned. |
| Does a title set with `Tab.async_set_title` survive the program setting its own title? | Yes. After an OSC 0 title from the program, the tab still showed the set title (`title` and `titleOverrideFormat` both "phase0 renamed tab"); only the session name changed. | Same spike | R16 as planned. |
| What do OSC 7501 reports put in the `status` variable? | `state=idle` gives `idle`; `working` gives `working`; `blocked` (with `kind=permission` or `kind=input`) gives `waiting`, and its base64 `msg` appears decoded as `detail` in `get_session_status`; `done` gives `done`; `error` gives `error`. `state=failed` is ignored. | Same spike and `spikes/osc_7501_error_state_spike.py` | Map exactly these five values. |
| What does OSC 21337 put in it? | Its free text, unchanged (`Working`, `Waiting`, `Idle`, and also `Compiling`). | Same spikes | Map known words case-insensitively; treat other text as no signal (as planned). |
| Do iTerm2 window frames and `NSScreen` share one coordinate system? | Yes: bottom-left origin, in points. A frame set to (100, 120, 800, 500) read back the same, and AppleScript's top-left bounds showed top = 709 = 1329 (screen height) − 120 − 500. Not yet checked on a second monitor. | Same spike | Section 10 as planned. |
| Does `App.terminal_windows` follow the front-to-back window order? | No. It stayed in creation order while different windows were brought to the front; `current_terminal_window` did follow the front window. | Same spike | Startup fallback needs macOS's window list (Quartz, `CGWindowListCopyWindowInfo`, matched by frame); while running, the core can track order itself from focus changes. |
| Does `Tab.async_move_to_window` fail for a window's only tab? | Yes: `RPCException('FAILED: Window has only one tab')`. | Same spike | Disable "Move to new window" for single-tab windows, as planned. |

### Claude Code 2.1.302 in a live test session

Run on the Haiku model with `--permission-mode default`, in a throwaway project folder whose own `.claude/settings.json` adds async logging hooks for 11 events (the user's settings were not changed). Scripts: `spikes/claude_code_agent_experiments_spike.py` and `spikes/claude_code_permission_experiments_spike.py`. The test commands use `perl`, because the user's allow rules let `echo`, `sleep` and `python3` run without asking; `--permission-mode default` still honors allow rules.

| Question | Answer | Effect on the plan |
|---|---|---|
| Where does the `status` variable come from for Claude Code? | From iTerm2's Claude Code integration, which is itself a set of user-level hooks: `~/.config/iterm2/cc-status` is registered in `~/.claude/settings.json` for 10 events (SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, Stop, StopFailure, SubagentStop, Notification, SessionEnd) and runs `it2 set-status --session=<GUID>` each time (plus an `osascript` call for a cookie). Claude Code itself contains no OSC 7501 or OSC 21337 text. Values seen: `idle`, `working`, `waiting`, `done`, and unset after the agent exits. One change had no hook behind it: `idle` about 3 s after Esc (its source was not found). | The status variable is not independent of hooks: it has the same gaps as hooks (below), and it exists only where iTerm2's integration is installed. |
| What does a nested `claude -p` (run by the tab's agent through its shell tool) do? | Its hook events carry a different `session_id` and parent PID but the same `ITERM_SESSION_ID`. Because iTerm2's integration hooks are user-level, the nested run also rewrites the tab's `status` (`idle`, `working`, `done`, `idle`) while the tab's own agent is still waiting for that tool call. The first spike was fooled by this itself: it took the nested `idle` as the end of the turn and typed `/exit` while the main agent was still working. | Ignore iTerm2's status for a tab while its own agent has a tool call open (a `PreToolUse` with no `PostToolUse` yet) or while another agent session in the same tab is active (hook events with another `session_id`, from its `SessionStart` until its `SessionEnd`). |
| What happens after a permission prompt is approved? | Nothing is reported until the tool finishes: the next hook event was the tool's `PostToolUse` (10 s later for a 10-second command), and `status` stayed `waiting` the whole time. | A new way for an open request to end is needed: the screen no longer shows the permission dialog. Without it, every approved tool call would keep the row "asking" until the tool ends. |
| What happens on Esc while an approved tool runs? | No hook event at all (no `Stop`, `PostToolUseFailure` or `StopFailure`). The screen shows `Interrupted · What should Claude do instead?`, and `status` became `idle` about 3 s later. | As planned: the newer `idle` ends the turn and the open request. The dialog check above ends the request sooner. |
| What happens when the user chooses "No"? | The menu in this version is `1. Yes`, `2. Yes, and don't ask again for: perl *`, `3. Yes, and switch to auto mode`, `4. No`, with `Esc to cancel · Tab to amend` (the first experiment's older layout had "No" at 3). Choosing No ends the turn at once with `Interrupted · What should Claude do instead?` and sends no hook event; the next text typed is a new prompt (`UserPromptSubmit`). `status` stayed `waiting` until that prompt. | The plan's special rule for "a denial with a comment lets the turn continue" is replaced by the dialog check. Menu numbers differ between versions, so nothing may type a number blindly (the app never answers permission prompts). |
| Does moving the tab to another window during a running tool call disturb the agent? | No. The tool finished, its output appeared, and the turn ended normally. | R18 as planned. |
| Hook order and timing | `PreToolUse` comes about 0.3 s before `PermissionRequest`. Each hook event arrived 0.2 to 0.5 s before the matching `status` change. After every `Stop`, an internal `SubagentStop` with an `agent_id` follows about 1 s later, with the main session's `session_id`. | Treat `SubagentStop` as the end of that `agent_id` only, never of the turn (already the rule, since state is kept per `agent_id`). |
| How does `/exit` end? | At the prompt: `SessionEnd` with reason `prompt_input_exit` after 0.9 s, `commandLine` changed after about 2 s, `status` went `idle`, then unset (two runs). `/exit` typed while a turn was still running gave reason `other` about 10 s later; a nested `claude -p` finishing also gives `other`. | `SessionEnd` arrives before the process is gone, so the 2-second grace is enough. Treat `prompt_input_exit` and `other` as normal exits. |
| What happens to keys typed when no dialog is showing? | They stay in the input box: a stray `1` became the start of the next prompt (`1Use the Bash tool...`). | Confirms the empty-input check before the app types `/compact` or `/clear` (section 8). |

### Codex in a live test session

Script: `spikes/codex_agent_experiments_spike.py`. The first two attempts ran Codex 0.154.0; during the second, the script pressed Enter while Codex showed its "Update available" menu, which ran `npm install -g @openai/codex` and updated Codex to 0.163.0 (the user chose to keep it). The script now turns off the update check for its run and refuses to type while any menu is showing. All results below are from 0.163.0, in a throwaway project folder with its own `.codex/hooks.json` (async logging hooks for 12 events), started with `--dangerously-bypass-hook-trust` (no hook approvals written), `-a on-request -s read-only`, and a prompt that asks the model to request escalated permissions so Codex asks before running the command. The folder had to be trusted through Codex's "Trust this folder?" question, which added one `[projects."<folder>"]` entry to `~/.codex/config.toml` per run; both entries were removed afterwards (approved by the user). Codex 0.163 also wrote two lines of its own to that file on its first start (`screen_reader_detection_done = true` and a counter for its "new model" notice); these were left in place.

| Question | Answer | Effect on the plan |
|---|---|---|
| What is Codex's `commandLine` and `jobName`? | 0.163: `jobName` `codex`, `commandLine` `codex <arguments>` (the job is the native binary). 0.154: `jobName` `node`, `commandLine` `node /opt/homebrew/bin/codex <arguments>`. | Match both forms, as planned (first word `codex`, or `node` followed by a path ending in `/codex`). |
| Does a Codex tab get a `status` value? | 0.163 yes, from Codex itself (its binary contains `ESC ] 7501 ; state=`): `idle` at the input box, `working` during a turn, `waiting` while its own approval menu is shown (0.1 s after the `PermissionRequest` hook), `working` 0.2 s after approval, `idle` at once after Esc or "No", unset after exit. 0.154 sent no status. | For Codex 0.163 and later, iTerm2's status is the main source and is accurate around approvals, unlike Claude Code's. Keep the screen fallback for older Codex versions. |
| Which hook file and options work? | A project's `.codex/hooks.json` is used once the folder is trusted; `"async": true` and `timeout` are accepted (both are fields of Codex's command hook). Events: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `Stop`, `SubagentStart`, `SubagentStop`, `Interrupt`, `SessionEnd`. Hooks run with the Codex process as their parent. Without `--dangerously-bypass-hook-trust`, new hooks wait for approval in `/hooks`. | The installer registers async hooks in `~/.codex/hooks.json`, as planned, and still ends with the `/hooks` approval step. |
| What do the hook payloads hold? | Every event: `session_id`, `transcript_path` (the rollout file), `cwd`, `hook_event_name`; turn events also `turn_id`, `model`, `permission_mode`. `UserPromptSubmit` has `prompt`; tool events have `tool_name` (`Bash`) and `tool_input` (`command`, plus `description` on `PermissionRequest`); `PreToolUse` and `PostToolUse` have `tool_use_id` but `PermissionRequest` does not (as in Claude Code); `PostToolUse` has `tool_response`; `Stop` has `last_assistant_message` and `stop_hook_active`; `SessionStart` has `source` (`startup`); `SessionEnd` has `reason`. | The forwarder keeps these fields, drops `tool_response`. The rollout file is found from `transcript_path`, not from `lsof` (below). |
| When does `SessionStart` fire? | Only when the first prompt is submitted, together with the first `UserPromptSubmit` (same 0.1 s, either order), not when Codex opens. | A newly opened Codex session has no hook events, so no `session_id`, until its first prompt. Its row relies on iTerm2's status until then. |
| What happens with this user's approval setting? | The user's `~/.codex/config.toml` has `approvals_reviewer = "auto_review"`. Then a `PermissionRequest` hook still fires, but an automatic reviewer decides (`Reviewing approval request` on screen), no menu appears, and `status` stays `working`. With `-c approvals_reviewer="user"` for one run, Codex showed its menu: `Would you like to run the following command?`, `1. Yes, proceed (y)`, `2. Yes, and don't ask again for commands that start with ... (p)`, `3. No, and tell Codex what to do differently (esc)`. | For Codex, a `PermissionRequest` hook alone does not mean the user is being asked. Asking comes from `status` = `waiting` (or, without status, the menu on screen). |
| What happens on approval, Esc and "No"? | Approval: no hook until `PostToolUse` (as in Claude Code), but `status` goes back to `working`. Esc while the approved command runs: an `Interrupt` hook 0.1 s later and `status` `idle`; the screen shows `Conversation interrupted`. "No": also an `Interrupt` hook, `status` `idle`, and `You canceled the request to run ...` on screen. In both interrupted runs a `perl -e sleep 40` process was still alive about 30 s after the interrupt, under the Codex process, although the screen said `Failed (exit 1)`. | `Interrupt` ends Codex's turn and its open requests, as planned. Background-process lights may show the leftover command. |
| Does moving the tab mid-command disturb Codex? | No: the command finished and its output appeared. | R18 as planned. |
| Does `codex queue --thread <session id> --message <text>` reach the running session? | Yes. It exits 0 with `Queued message <id> for thread <id>.` and the idle session in the iTerm2 tab ran it as a normal turn (`UserPromptSubmit`, `Stop`) 1 s later in one run and 9 s later in the other. The session ID comes from any hook payload. | The introductions feature (section 18) can deliver to Codex with `codex queue`, so its Codex part is Small. |
| How does `/quit` end? | `SessionEnd` with reason `other` 0.4 s later; `status` unset 0.5 s later; the process exited 5 to 7 s later (Codex shuts down its MCP servers first). | `SessionEnd` comes well before the process is gone, so the row should end on the event itself (section 6, "Ending"). |
| Does the `codex` process keep its session file open? | No. `lsof` showed Codex's SQLite files (`state_5.sqlite`, `logs_2.sqlite`, `queue_1.sqlite`, `thread_history_1.sqlite` and others) but not the rollout file. | Find the rollout file from the hooks' `transcript_path`, or by the session ID in its file name. |

### Typing slash commands, the input box, and screens during a long turn

Script: `spikes/slash_commands_and_long_turn_screens_spike.py` (run once per tool; Claude Code 2.1.302 on Haiku, Codex 0.163.0). The Codex run's folder trust entry was removed from `~/.codex/config.toml` afterwards.

| Question | Answer | Effect on the plan |
|---|---|---|
| Does typing the command, a pause, then a separate Enter submit `/compact` and `/clear`? | Yes in both tools, with a 150 ms pause for Claude Code and 300 ms for Codex. Typing the command opens the slash-command menu with the exact command highlighted first (Claude Code also lists `/autocompact`), and Enter runs it. | As planned (section 8). |
| What does an empty input box look like? | Both tools show dimmed text in it: Claude Code `❯` + no-break space + `Try "refactor <filepath>"` (or, after a turn, sometimes a suggested next prompt), Codex `›` + `Ask Codex to do anything`. The screen read reports these cells as faint; a typed draft (`phase0 draft text`) is not faint in either tool. Codex also draws braille-dot characters (U+2800 to U+28FF) as an idle animation, inside and around the box. Earlier prompts in the transcript start with the same marker. | The empty check ignores faint cells and, for Codex, braille dots, and finds the input line as the last marker line directly above the box's lower edge (section 8). |
| What follows `/compact` and `/clear`? | Claude Code `/compact`: `PreCompact` (`trigger` `manual`), then `SessionStart` with `source` `compact` 4 to 7 s later, same session ID, and no `status` change in between. Claude Code `/clear`: `SessionEnd` (`reason` `clear`) and 0.4 s later `SessionStart` (`source` `clear`) with a new session ID and transcript, same process. Codex `/compact`: `PreCompact`, then `PostCompact` about 4 s later, with `status` `working` in between. Codex `/clear`: no hook event and a new chat; at `/quit`, one `SessionEnd` per chat. | A `clear` session end must not remove the row; "compacting" is shown from the hooks (sections 6 and 8). |
| Which lines change every second during a long command with no progress? | Claude Code: the spinner glyph (`✳ ✶ ✢ ✻`), the counts in `Thinking… (5s · ↓ 97 tokens)`, the ` · 4s` suffix of the tool line, the `(4s)` suffix of the command line, and the tool line's `⏺` bullet, which blinks on and off. `(ctrl+b to run in background)` appears after a few seconds. Codex: the elapsed time in `Working (5s • esc to interrupt) · 1 background terminal running`, and its braille-dot animation. | Fixtures for `progress_noise_pattern` (section 6). |
| Anything else? | Claude Code 2.1.302 refused to run a standalone `sleep 45` ("standalone sleeps" are blocked); `python3 -c "import time; time.sleep(45)"` ran. | Only matters for tests. |
